# module-design — 模块详细设计

## 定位

把「概念案 + 可玩原型」细化为**可直接指导开发**的模块级设计文档。

判断完成的标准只有一个：**一个没参与过讨论的开发者，只读这份文档能否看懂并照着实现。**

---

## 工作方式

1. 通读上游上下文（一页纸概念案、核心循环、原型说明），确定游戏由哪些模块组成（战斗、成长、关卡、经济、社交、UI 等，按游戏实际形态划分，**不要照抄本文档的举例**）。
2. **先派子 agent 做检查，再定稿**：文档主体写完后，启动子 agent 做两类检查，并根据反馈修订：
   - **逻辑闭环检查**：各模块的规则、状态流转、数值口径是否自洽；模块之间的依赖与调用关系是否闭环；有没有「定义了却没人用」或「用了却没定义」的机制。
   - **可读性检查**：一个没参与过讨论的开发者，只读这份文档能否看懂并照着实现；找出歧义、跳步、术语未解释的地方。
3. 修订完成后输出最终文档。**不要输出检查过程的流水账。**

---

## 输出结构

### 开头：名词与含义（必写，放最前）

用表格列出文档中出现的所有专有名词/术语：

| 名词 | 含义 |
|---|---|

后文一律使用表内名词，含义以本表为准。非必要不使用英文；确需英文的（如通行行业术语）在含义列给出中文解释。

### 总览

- 模块划分表 / 列表：每个模块一句话说明它负责什么、和哪些模块有交互

### 各模块详设

先总览后分模块。每个模块按以下结构展开：

#### `<模块名>`

- **定位与职责**：这个模块解决什么问题
- **游戏逻辑**：规则、状态、流转、判定，写清**输入 → 处理 → 输出**
- **游戏交互**：玩家怎么操作、界面如何反馈、操作与逻辑的对应关系
- **表现与反馈**：动画、镜头、UI 表现，以及**音频/音效**（什么时机播什么声音、音乐风格）、**视频**（如有过场/演出）
- **与其他模块的关系**：依赖谁、被谁依赖、数据怎么流动
- **边界与异常**：极端情况、非法输入、断线重连等如何处理

---

## 约束

- **总分结构**：先总览后分模块；每个模块先定位后细节。
- **人类阅读友好**：多用列表和表格，少堆大段文字；**一个规则只在一处定义**，其他地方引用。
- 非必要不使用英文；术语必须与开头名词表一致。
- 覆盖面必须包含：游戏逻辑、游戏交互、音频、音效；有视频 / 演出需求时也要写明。
- 直接输出文档本身。

---

## 覆盖度自检

设计文档必须触及以下全部维度，缺一项就是漏了：

- [ ] **玩法规则**：判定条件、状态机、数值口径
- [ ] **交互反馈**：每个操作对应的界面变化
- [ ] **音频**：BGM 分层/切换时机、音效触发点、音量与优先级
- [ ] **成长与解锁**：玩家变强的路径、卡点设计
- [ ] **经济与资源**：获取与消耗的入口和出口
- [ ] **异常处理**：非法输入、断线重连、资源不足、越界
- [ ] **模块间数据流**：谁读谁的数据、什么时候读写

## 与其他技能的衔接

本技能的产出会被下游直接消费：

| 下游技能 | 从本技能取什么 |
|---|---|
| `numeric-balance` | 模块的数值口径、资源定义、成长路径 |
| `ui-design` | 「各模块详设」的模块清单 → **每个模块标题就是一个 UI 原型** |
| `config-tables` | 所有需要外部配置的实体与数值 |
| `player-review` | 完整设计资料 |

> **给 `ui-design` 的约定**：模块清单按结构提取 —— 找「各模块详设」节（任意 `#` 级别），取其下**低一级**的标题作为模块。`## 总览` 节下的标题（模块划分表、数据流图、数值真源清单）**不是模块**。

产物写入 `specs/<project>/03-design/module-design.md`。
