# ui-design — 游戏 UI 设计与文案

## 定位

两件事：**让界面一眼看懂**，以及**让团队看到界面长什么样、信息怎么分层**。

UI 的目标是让玩家「一眼理解」，而不是解释系统。

**优先级：**

```
图标 > 数字 > 进度条 > 短词 > 短句 > 长文本
```

能用视觉元素表达的信息，禁止使用长句解释。

> 本技能的完整硬性规范见 `references/ui-copy-constraints.md`（逐字内置，与本文件冲突时以 references 为准）。

---

## 第一部分：产出模块 UI 原型

### 模块清单提取

从「模块详细设计」文档定位「各模块详设」这一节。

**按结构判断，不按固定层级**：先找到「各模块详设」这个节标题（任意 `#` 级别），再取它下面比它**低一级**的标题作为模块。

> 例：`# 各模块详设` + `## M1 …`；或 `## 各模块详设` + `### 模块 01｜…`

**模块名逐字照抄**标题文字（去掉 `#` 号本身）：不改写、不翻译、不删掉 `模块 01｜` 这类前缀、不去掉括号里的补充说明。它同时是原型文件的文件名主体。

唯一例外：标题里出现文件名非法字符 `/ \ : * ? " < > |` 时，把它们**替换成 `·`**（其余字符一律保留）。
例：`模块 06｜成长与 Meta（档案 / 段位 / 战绩 / 收集度）` → 文件名主体 `模块 06｜成长与 Meta（档案 · 段位 · 战绩 · 收集度）`。

> 文件名里绝不能出现 `/` —— 那是目录分隔符，产物会落错地方。

**常见坑**：`## 总览` 节下的标题（模块划分表、数据流图、数值真源清单）**不是模块**，不要为它们生成原型。

如果找不到「各模块详设」这一节，或该节下没有任何模块标题，**直接说明情况并停止**，不要自行编造模块清单。

如果用户只点名了某个模块，就**只写该模块的那一个文件**，其他模块的现有文件一个字都不要动。

---

### 原型定位：只做展示，不做逻辑

这不是能玩的游戏，是一张「可以点的界面稿」。

| | 内容 |
|---|---|
| **允许** | 用纯前端交互切换页签 / 打开关闭弹层 / 高亮选中项 —— 目的是让评审者看到不同界面状态 |
| **禁止** | 玩法逻辑、数值计算与结算、真实数据请求、音效、动画库、任何外部资源（CDN / 字体 / 图片外链一律不许，图标用 emoji 或 CSS 画） |

页面里的数字 / 文本一律是**写死的 mock 数据**，看起来合理即可，不需要与配置表严格对齐。

### 每个原型页面的内容

覆盖该模块**主要的界面状态**，通常包括：

- **主界面**：玩家进入该模块后第一眼看到的画面（HUD / 主面板）
- **关键子界面或弹层**：该模块最重要的 1~2 个二级界面（详情页、确认弹层、列表页等），用页签或按钮切换展示

### 页面骨架

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>模块 UI 原型 · <模块名></title>
</head>
<body>
  <!-- 模块 UI 原型：<模块名> —— 版本 v<N>，仅展示，无逻辑 -->
  <!-- 醒目位置标注「原型 · 仅展示」 -->
  ...
</body>
</html>
```

**硬性要求：**

- 完整单文件，CSS / JS 内联
- 页面顶部注释写明：模块名、版本号、`仅展示，无逻辑`
- 页面内一个**可见的角标**标明「原型 · 仅展示」，避免被误当成可玩版本
- 竖屏手游：内容放进居中、最大宽度约 480px 的容器里；横屏：铺满视口
- 触控与鼠标都能点
- 中文文案

---

### 文案要求落到实操

- 单个 UI 模块的文字尽量 **≤5 个字**，一句话 **≤10 字**；能用图标 / 数字 / 进度条表达就不要写文字
- 信息分四级：**即时信息**（HP / 金币 / 时间，主界面显眼处）→ **操作信息**（1~4 字按钮）→ **解释信息**（Tooltip / 弹层 / 详情页，**不要放主界面**）→ **背景信息**（不进 UI）
- 不为了填满空白加标题、副标题、说明文字。**留白本身就是设计**
- 一个页面只有一个视觉焦点，不要让所有元素权重相同
- 信息多时**删减或分层**，不要把字号缩小硬塞
- 视觉风格克制：统一色板（3~4 个主色）+ 少量中性色，不要花哨渐变与多层嵌套面板

---

### 禁止晦涩、书面化表达

| ❌ 禁止 | ✅ 改为 |
|---|---|
| 当前生命值已低于安全阈值 | 低血 |
| 该技能将在冷却结束后再次可用 | 冷却 3.2s |
| 你的金币数量不足以购买该物品 | 金币不足 |
| 按下该按钮以打开角色装备界面 | 装备 |

禁用词句：「当前处于……状态」「请注意……」「该功能允许玩家……」「目前无法……」「建议您……」「该资源可用于……」「您当前拥有……」「进入该区域后……」。

## 第二部分：减法检查（每次生成 UI 后必做）

主动检查，答案是「可以删除」就删除：

- [ ] 有没有可以删除的文字？
- [ ] 有没有可以用图标代替的文字？
- [ ] 有没有重复信息？
- [ ] 有没有不必要的标题 / 副标题 / 说明？
- [ ] 有没有可以移到 Tooltip 的信息？
- [ ] 有没有为了填空间而添加的元素？
- [ ] 玩家能否在 **1~2 秒内**理解这个界面？

**最终 UI 应该尽可能简单，而不是尽可能完整。**

---

## 信息过多时的处理顺序

**不要把内容缩小塞进去。** 按序尝试：

1. 删除非必要信息
2. 合并重复信息
3. 使用图标代替文字
4. 使用 Tooltip
5. 折叠 / 分页
6. 将次要信息移动到详情页

宁愿少展示，也不要做成信息墙。

---

## 视觉风格优先级

1. 可读性
2. 信息层级
3. 操作效率
4. 一致性
5. 美观

**不要为了「看起来很丰富」增加元素。克制比堆砌更重要。**
